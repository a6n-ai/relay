## Learned User Preferences

- Relay follows `DESIGN.md` at the repo root (Linear design language, owner 2026-11-10). Read it before any UI change; it beats every older note here. Never TiffinGrab orange/cream.
- Lavender `#5e6ad2` is the one hue, used generously on interaction and data (actions, active nav, hover/selection tints, focus, charts). Dark is the default theme; light mirrors it.
- Always reuse: build screens from `components/ds` (Panel, StatusBadge, IconTile, SectionTabs, ListingTable, OperatorSplit…), `@foundry/design-system` and `@foundry/ui`, styled only through tokens. A pattern used twice becomes a component; no one-off class strings on pages. Collection pages use `ListingTable` as a thin adapter over Foundry/Realm `DataTable` + `FilterPill` chips (Beautiful UI Filter Table ref); columnar/sortable grids use `DataTable` directly (Records Table ref). Do not add a second Foundry table primitive. Shadcn Dashboard and beautifului.dev are visual refs only — do not vendor their dumps.
- Shadcn Dashboard blocks (shadcndashboard.dev) are visual/layout reference only (including Dashboard Shell 03 analytics). Implement with Foundry primitives plus Relay DS; do not vendor dumped `components/ui` or ecommerce dummy blocks as the source of truth.
- Do not push `.cursor/` MCP/AI config to GitHub.
- Use semantic design tokens (`bg-primary`, etc.), not raw color utilities. Buttons share one Linear-style full pill radius via tokens (`9999px` / `rounded-full`) on operator UI and public/marketing; inputs and cards stay at the moderate radius.
- Use Foundry data-access (`UpdatableRepository`, `SessionUpdatableService`) and `@foundry/routes` for operator CRUD, not ad-hoc Drizzle on those paths.
- Tenants are consuming apps: monthly send quota, channel-scoped API tokens, and verified tenant senders (unverified From falls back to operator). A tenant domain can mint send-as addresses or Relay inboxes; people IMAP inboxes stay a later roster. Email first; operator SMTP/domains/From live in Settings.
- Operator chrome must stay non-technical. The sidebar is 8 grouped links (components/ds/nav.ts): Overview: Home, Inbox; Reach people: Campaigns, People; Activity: Sends; Setup: Apps, Channels, Settings — then Organization at the bottom (Clients for `super_admin`, Team for everyone). Templates/Automations, Status updates, the four channels, and Email sending/Tags/Your account are tabs (SectionTabs) inside the product links; Clients/Team share Organization tabs. Keep product links at 8 or fewer. Never SMTP, IMAP, webhook, outbox, tenant, POST /v1, Foundry, or skip locked in the UI. Routes and schema keep those names.
- Operator listings share search plus filter chips (client-side over loaded rows). Empty catalogs stay a plain empty state until there is something to narrow.
- Collection pages use a shared create/browse split (`OperatorSplit`) and hairline resource rows, not per-page stacked cards. Linear shell: `ViewHeader` title row (~44px breadcrumb + actions) with a view row for `SectionTabs`; `CreateDialog` is top-anchored and closes on successful save with a toast.
- Public landing (`components/marketing/`) follows Linear.app homepage patterns: Hairline figures with stageshow kit and GSAP ScrollTrigger; figure ground fills match page `--background` (`#0f1011` dark / `#fbfbfc` light).

## Learned Workspace Facts

- Relay is a Next.js operator console for multi-channel notifications at `http://localhost:3010` (`/` → `/dashboard`, unauthenticated → `/login`). Better Auth sign-up is disabled; the seed operator is the local login path. Local UI verify often uses `next dev -p 4500` (Better Auth trusted origin); production is `relay.a6n.ai`.
- Workspaces are Better Auth organizations (`organization` / `member` / `invitation`); UI says “Workspace”. Session `activeOrganizationId` scopes the console. Apps (`tenants`) carry `organizationId` and list/create only for the active workspace. Sidebar has Workspace and App switchers (workspace first / team, then app / product being operated on). New workspaces start empty — no auto-created app; after create, land on Apps with empty copy to start by creating an app. Do not use Better Auth Infra / `dash()` — platform client listing is Relay-native. a6n platform uses `@foundry/auth` `platformRole` (`super_admin`) + `resolveVisibleOrgIds`; Clients live at `/dashboard/platform` (separate from the 8 product nav links; sidebar a6n → Clients for `super_admin`). Client orgs carry workspace limits (`monthlyMessageQuota`, `maxApps`; 0 = unlimited) set on create/manage; enforce max apps on tenant create and org monthly quota on `POST /v1/messages` (in addition to per-app quotas). Clients list marks the active workspace Current. Organization (sidebar bottom): Clients (`/dashboard/platform`, `super_admin`) and Team (`/dashboard/accounts`, active-workspace `member` rows). Your account stays Settings → `/dashboard/account`. Seed creates workspace `a6n`, attaches orphan apps, and sets seed ops to `super_admin`.
- Data layer is Postgres + Drizzle. Local env lives in `apps/relay/.env.local` (gitignored).
- Turbopack root is `a6n-ai` (parent of this repo) so Tailwind can `@source` sibling Foundry packages. Git-hosted `@foundry/*` packages ship TypeScript source and must stay in `transpilePackages`.
- Pin `shadcn@4.11.0` so CSS (`shadcn/dist/tailwind.css`) resolves under that Turbopack root.
- Relay DS lives under `apps/relay/components/ds` (`OperatorSplit`, `ResourceBoard`/`ResourceRow`, listing search/filter); UI primitives come from `@foundry/ui`. `.cursor/` is gitignored.
- Queue is Postgres `notification_outbox` with SKIP LOCKED drain/retry (no Redis/RabbitMQ). Claim-and-process work and identity-less joins stay as explicit Drizzle transactions.
- Public send API is `POST /v1/messages` (hashed `api_keys`). Operator CRUD uses Foundry services; `campaign_tenant` is a Foundry entity (`ctn_` public ids).
- Operator email transport/From/domains live at `/dashboard/settings/email` (old `/dashboard/domains` and `/dashboard/sending` redirect). Tenant senders verify via domain DNS.
- Mailbox at `/dashboard/mailbox` is conversations in Postgres `email_mailbox` (sent + received), chip-filtered by origin (Relay sent / Automatic / Campaigns / Failed) and Received. Threads use Message-ID / In-Reply-To; Reply stays on the thread. Compose/Reply uses the send stack and verified Froms. Inbound is a signed provider webhook, not a port-25 listener. IMAP and hosted `you@domain` accounts are not in Next.js; Stalwart/Mail.app is optional later on a people domain. `@foundry/email` is send only — do not merge mailbox hosting into it, and do not put people-mail MX on the transactional sending domain.
- Message tags belong to an app and mark every message from that app (mail now, later channels later). Operators manage them at `/dashboard/settings/tags`; Mailbox chips reuse the same tags. Letters with no app cannot take those tags.
- On memory-limited Macs, run only one Node-heavy command at a time with `NODE_OPTIONS=--max-old-space-size=4096`; never run `next build` concurrently with `next dev` or other heavy Node.
